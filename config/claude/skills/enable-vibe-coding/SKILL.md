# Enable Vibe Coding

Run the implementation checklist as a sequence of delegated PRs. The `/enable-vibe-coding` entry point may enable session vibe mode before this skill runs. Armyknife repository policy limits unattended review and merge to repositories where `repo.vibe` is `true`.

When this session acts as a PM and the user asks to start vibe coding (including via `/enable-vibe-coding`), do not run the loop here. Follow the `project-manager` skill's procedure to ensure the PM's effective vibe is active. Unless the user limits the target, include every worker the PM has assigned. Reuse existing target workers, grant every existing target worker without inferring whether it already has inheritance eligibility, and notify them only after all grants finish. Start a new worker through the established handoff launcher only when needed; Armyknife records its inheritance eligibility automatically when the caller's effective vibe is active at launch, so do not grant that worker. Notify every target worker to run this skill.

## Start

1. Resolve the tq task ID in this order: use `$ARGUMENTS` when supplied; otherwise use the current branch's `branch.<name>.x-tq-task-id` when set; otherwise use the unique leaf task linked to `$TQ_SESSION_ID` via `tq session list`. Reduce linked tasks to leaves with `jq`. If more than one leaf remains, ask the user which task to run. If none remains, follow the `track-in-tq` skill's start procedure to find or create the task and link this session, without asking the user: invoking this skill already means the work should run, and `track-in-tq` owns the find-or-create decision. Create a task only when this session has an agreed design; otherwise stop before creating one, because step 3 would stop on it anyway and leave an empty task behind.
2. Resolve each leaf's target repository from its note. In that repository, run `a config get repo.vibe` and record the effective result for the leaf. Require a boolean result; if the command fails or returns anything else, treat the result as `false` and use normal delegation for that leaf. Continue with other leaves. Never assume vibe is allowed. Delegate every leaf through a worktree and a PR, even when the repository's `repo.direct_commit` is `true`; the delegate skill's vibe rules cover this.
3. Pass your model name with `--author` on every `tq` command. Read the task with `tq task get <task-id>`. Read the task's design page with `tq page list` and `tq page get`; use `--output` and a path created with `mktemp "$AGENT_TMPDIR/tq-page.XXXXXX"` for a long page. If there is none, write the design agreed in this session as the design page, following `track-in-tq`; stop only if no design has been agreed. Require exactly one checklist named `実装` and read its leaves and notes. If there is none, record the split with the `split-into-prs` skill, passing the step 1 task as its target task. An agreed design counts as the split's approval only when it already lays out each PR's scope, goal, and dependencies.
4. Confirm the `実装` checklist has at least one unchecked leaf. If every leaf is checked, report that the task is already complete. Vibe mode may already be enabled when this check runs.
5. Follow the `delegate` skill to prepare the prompts for every unchecked leaf whose `依存` note is resolved. Keep all prepared payloads for dispatch; do not start delegates during this check.
6. If at least one ready leaf has `repo.vibe: true`, run `a agent vibe status` before dispatching those leaves. If it succeeds, continue without running `a agent vibe on`. If it fails, run `a agent vibe on` and confirm `a agent vibe status` succeeds. If `a agent vibe on` or the follow-up status check fails, tell the user which ready leaves are held and which command failed, then hold those leaves and continue with normal leaves. If every ready leaf has `repo.vibe: false`, skip these commands and use the normal delegation flow.
7. Dispatch each prepared task with `~/.agents/skills/delegate/scripts/launch`, passing `--task`, `--repo`, `--label`, `--tq-task-id`, and the leaf's `--tq-checklist-item-id`. Add `--vibe` only for leaves whose target repo has `repo.vibe: true`; omit it for normal leaves. The launcher fixes delegate type and worktree policy. A normal delegate follows the regular human review and merge flow. The user reviews and merges its PR; do not handle it as a vibe report, submit it, or merge it. Keep dispatching other ready leaves and handling active vibe delegates without waiting for a normal PR. Only leaves that depend on a normal PR remain blocked until the user merges it and the checklist reflects completion. For every later newly ready leaf, repeat the repo policy check from step 2, then confirm step 6 succeeded before dispatching a vibe-enabled leaf. Do not delegate parent items or leaves with unresolved dependencies.

Treat a dependency as resolved only when the referenced checklist work is checked and any stated release or merge requirement is satisfied. When a note has no dependency, or says `依存: なし`, the leaf is ready. If a dependency is ambiguous, leave that leaf undispatched until it can be verified.

The following vibe report and merge procedures apply only to checklist leaves or CI repairs whose target repo has `repo.vibe: true`. A normal delegate, including a repair in a repo where vibe is disabled, does not send vibe reports. Leave its review and merge to the user, and do not run `a gh pr-merge` for its PR.

### Review against purpose and design

For checklist PRs, use the exact tq task description, design page, and item note as context. Compare the implementation with the original purpose and explicit user instructions and the approved design. Treat the design as a plan for meeting that purpose: do not flag a purpose-aligned improvement solely because it differs from the design, and flag a design-following implementation that departs from the purpose or explicit instructions. For CI repairs, use the failed run and repair task to identify the purpose and explicit instructions, and assess the implementation against them without requiring an approved design. Distinguish user requirements from agent proposals and assumptions. Leave general code quality to the delegate's self-review.

## When a `<vibe-draft-ready>` report arrives

Handle each report once. A report must contain the absolute draft path, branch name, head SHA, and checklist item ID. Match the item ID to an active delegate and its task note. A checklist leaf must report its exact item ID; if it reports `none` or a different ID, treat that as a broken premise and ask the delegate to correct it and resend. A default-branch CI repair has no checklist item; its report must identify that repair and include `checklist item ID: none`. Match it to the active repair delegate. If a report is missing any required value, ask the delegate to resend it in the `create-pr` format; if it does not match an active delegate, resolve it as described under `When something goes wrong`.

1. Confirm the reported head SHA exists in the target repository and is the tip of the reported branch. Read the draft from its absolute path and obtain the diff with `git diff origin/$(git main)...<head-sha>`. For a checklist PR, read the exact tq task description, design page, and item note. For a CI repair, use the failed run and repair task as the review context instead. Read `~/.agents/skills/create-pr/SKILL.md` and `~/.agents/skills/create-pr/references/draft-manual.md`. Run `~/.agents/skills/create-pr/scripts/render-rules` from the target repository root. If any required file or command is unavailable, stop as described under `Stop conditions`.
2. Ask a read-only subagent to review the draft as the user would in Step 3 of `create-pr`. Give it the draft, diff, exact tq task description, design page, and item note (or the CI repair context), `create-pr/SKILL.md`, `create-pr/references/draft-manual.md`, and the rendered rules; tell it to read the skill and reference. Require separate findings for PR content and implementation alignment, with concrete evidence. Tell the subagent not to edit files or interact with GitHub. Apply the review criteria above to implementation alignment.
3. If the PR body has findings, insert plain-language comments at the relevant places in the reported draft, as a reviewer would in the `a ai pr-draft review` editor. There is no special marker. Then notify the delegate that the draft contains comments and must be revised through the `create-pr` skill's Step 4. If the diff has findings, notify the delegate to fix the code. Include both sets of findings when both reviews fail. Do not approve the draft while either review has findings.
4. If both reviews pass, record the approved head SHA for this PR and notify the delegate that it is approved and may be submitted.

## When a `<vibe-pr-ready>` report arrives

A report must contain the PR URL, checklist item ID, and head SHA. For a checklist leaf, require its exact item ID; if the report says `none` or gives a different ID, treat that as a broken premise and ask the delegate to correct it and resend. For a CI repair, require `checklist item ID: none`. Match the report to the active delegate and its approved draft review. If a report is malformed, ask the delegate to resend it in the `create-pr` format; if it does not match an active delegate, resolve it as described under `When something goes wrong`.

1. Confirm that `gh pr view <pr> --json headRefOid -q .headRefOid` exactly matches the reported head SHA. If it does not, do not review or merge that report; ask the delegate for a fresh PR-ready report with the current SHA. Compare the reported SHA with the SHA approved during draft review. If they differ and the approved SHA is an ancestor of the reported SHA, obtain the incremental diff with `git diff <approved-sha>..<reported-head-sha>`. If the approved SHA is not an ancestor, the branch was rebased or rewritten; obtain the current PR-only diff with `git diff origin/$(git main)...<reported-head-sha>` and review that full diff. For a checklist PR, read the exact tq task description, design page, and item note; for a CI repair, use the failed run and repair task as the review context. Ask a read-only subagent to compare the applicable diff using the review criteria above. If the comparison has findings, notify the delegate to fix the code. If it passes, record the reported head SHA as approved.
2. If the PR has a `vrt` commit status, get its state and target URL with `gh api repos/<owner>/<repo>/commits/<head-sha>/status --jq '.statuses[] | select(.context == "vrt") | {state, description, target_url}'`. If the status is pending, wait for it to finish and fetch the status again before opening the report. Then inspect every changed image in the reg-suit report. Compare each image with the approved context from Step 1: the exact tq task description, design page, and item note for a checklist PR, or the failed run and repair task for a CI repair. Apply the review criteria above; do not infer intent from the code diff or PR body alone. If the report has no changed images and `vrt` is already successful, continue without a label. Skip this step if the PR has no `vrt` status.
    - If every visual change is intended, check for the exact `vrt-agent-reviewed` label with `gh label list --repo <owner>/<repo> --search vrt-agent-reviewed --limit 5000 --json name`. If it is missing, create it with `gh label create vrt-agent-reviewed --repo <owner>/<repo> --description "VRT diff reviewed by an agent"`. Then add it to the PR with `gh pr edit <pr> --add-label vrt-agent-reviewed`. Wait until the `vrt` status for the reported head SHA is successful before continuing. This label records the agent's review. Never add `vrt-approved`, which is reserved for human approval.
    - If any visual change is unintended, do not add `vrt-agent-reviewed`. Notify the delegate with the affected images and concrete findings, ask it to fix the code, and review the new `<vibe-pr-ready>` report.
    - If the report or its images cannot be opened, or `vrt` fails without a visual diff report, notify the delegate to restore or fix the report and send a fresh `<vibe-pr-ready>` report. Do not ask the user to review the VRT.
3. Verify with `gh pr checks <pr>` that all required checks are green. If checks are pending, wait for the delegate to finish them; do not merge yet. If a check failed, notify the delegate with the failed check and wait for a corrected ready report.
4. Before merging, read the title with `gh pr view <pr> --json title -q .title`. If it matches Conventional Commits breaking-change syntax (`type!:` or `type(scope)!:`), stop under `Stop conditions` without attempting the merge and ask the user to merge this PR. Otherwise, repeat `gh pr view <pr> --json headRefOid -q .headRefOid` immediately before merging and require an exact match with the approved SHA. If the SHA changed, do not merge; ask the delegate for a fresh PR-ready report and review the new changes. If the SHA still matches and required checks are green, run `a gh pr-merge <pr>` from the target repository. Do not use `gh pr merge`.

## After a merge

1. Follow the `delegate` skill's merge procedure to confirm CI on the default branch is green. This also applies after the user merges a normal delegate's PR; do not merge that PR yourself. A merge notification for a PR this skill already merged is informational; do not process it as a new merge.
2. If default-branch CI fails, pause merges and new delegations. Notify active repository sessions to hold their merges. Resolve the affected repo's policy using the `a config get repo.vibe` lookup in `Start` step 2. If it resolves to `true`, launch a CI repair with the delegate launcher and `--vibe`, then review and merge it through the vibe draft and PR procedures; otherwise, launch a normal repair without `--vibe`, which the user reviews and merges. Do not associate the repair with a checklist item; pass the task chosen in the `delegate` merge procedure's step 2-3 as `--tq-task-id`. After the repair merges, check default-branch CI again and resume held sessions when it is green. If the repair delegation fails, retry using the same repo policy.
3. Refresh `tq task get <task-id>` and confirm the merged checklist leaf is checked. If it remains unchecked, stop before redispatching that item and resolve the tq state.
4. Re-read the checklist. Dispatch every newly ready unchecked leaf in parallel, using the `Start` procedure's dependency rules. Keep already active delegates running.
5. Continue handling ready reports, merges, CI, and newly unblocked leaves until all leaves in `実装` are checked. When waiting for a normal PR's user review or merge, continue any independent ready work; only its dependents wait.

## When something goes wrong

Resolve these yourself and keep the loop running; do not ask the user unless a `Stop condition` applies.

- A delegate reports that a supplied premise is wrong: re-investigate, correct the premise (update the item note or design page when they were wrong), and notify the delegate with the correction.
- `a gh pr-merge` fails: if a `Stop condition` applies, stop as instructed there. Otherwise, for a conflict, tell the delegate to sync the base branch with the `sync-base-branch` skill; for a failed required check, tell the delegate to fix it; for any other failure, read the error and fix its cause or have the delegate fix it. Then handle its next PR-ready report.
- A report, PR, or delegate cannot be matched: identify it from `a agent peer children`, the branch's `x-tq-checklist-item-id`, and `gh pr list`, then continue.

## Stop conditions

- A file or command required for draft review is unavailable.
- The PR title marks a breaking change. Do not attempt the merge; ask the user to merge the PR.

When stopping, report the reason and the next decision needed to the user, then run `a agent status set you "<the decision needed, as a noun phrase>"`. Leave vibe mode on and wait for the user's direction. Do not continue merging or dispatching work while waiting.

When every leaf is checked, report completion to the user. Leave vibe mode on; the user may still give follow-up work in this session. Run `a agent vibe off` only when the user asks for it.
