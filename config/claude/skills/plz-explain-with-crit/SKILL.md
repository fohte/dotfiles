# crit で PR を解説する

crit を「レビューツール」としてではなく、「コードの意味を質問できる UI」として使うためのワークフローである。
ユーザーは Approve するかどうかを判断したいのではなく、単にコードを理解したいだけである。
通常のレビュー運用 (approve に向けて指摘を潰していく) とは目的が違う。

## 全体の流れ

1. 対象リポジトリで `crit --pr <num>` をバックグラウンド起動する
2. 起動ログの URL をユーザーに案内する
3. (依頼があれば) 過去の履歴を消してから開き直す
4. バックグラウンドタスクの完了通知を待つ
5. 通知に含まれるコメント (=ユーザーの質問) を読み、該当コードを調査する
6. 回答を crit 側への返信として書き込む (チャットには書かない)

## 1. 起動する

対象リポジトリがローカルに無ければ用意する (owned org なら `ghq get -u`)。
リポジトリ内で以下を実行する。

```
crit --pr <num>
```

**これは Web UI サーバーを起動してブラウザ操作を待ち続ける、フォアグラウンドでは終了しないコマンドである。**
普通に Bash 実行すると呼び出し元がブロックされ続ける。
必ず `run_in_background: true` で実行すること。

`--no-open` を付けるとブラウザが自動起動しなくなる。
付けるにせよ付けないにせよ、Claude 側からブラウザを開く手段はない。
**起動ログに出る `http://localhost:<port>` を必ずチャットで案内すること。**
「crit が起動しました」で終わらせて URL を書き忘れると、ユーザーは何も操作できない。

## 2. 履歴を消していちから開き直す

crit は同じ PR (`focus_key: pr:<num>`) に対して過去に開いたセッションを自動的に再利用する。
Round 数が増え、diff から外れた古いコメントが Outdated として残り続ける。
ユーザーが「いちから」「クリーンな状態で」と言った場合はこれを消す。

対象リポジトリのディレクトリで以下を実行する。

```
crit status --json   # review_file のパスと session id を確認
crit stop            # 対象セッションの daemon だけを止める
```

`--all` を付けると他の無関係な crit セッションまで巻き込んで停止させてしまうので使わない。
`crit status --json` の `review_file` (`~/.crit/reviews/<session-id>/review.json`) がまだ残っていれば、そのディレクトリを削除する。
これは git 管理下のファイルではなく crit のローカルキャッシュなので、消してよい。
その後もう一度 `crit --pr <num>` を起動すれば、真っさらな状態で開ける。

## 3. ユーザーの質問を拾う

バックグラウンドの `crit --pr` プロセスは、ユーザーがブラウザ側で一定の操作 (Approve など) をすると終了し、タスク完了通知が届く。
**通知が来るまで sleep やポーリングで待たず、何もツールを呼ばずに待つこと。**

完了時の stdout に `approved: true/false` と、未解決コメントの一覧が JSON で入っている。
これがユーザーの質問そのものである。
ここで会話が完結したと思って放置してはならない。
中身を読んで次のステップに進む。

## 4. 調査して crit に返信する

質問ごとに、実際に該当コードを読んで理解してから答える。
憶測で代弁しない。

- 該当ファイルを Read するか、`gh pr diff <num> --repo <owner>/<repo>` で PR 全体の diff を見て文脈を掴む
- コミットメッセージや周辺コードから、その変更が何のためのものかを把握する

回答は crit 側への返信として書き込む。
**チャットに解説を書いて済ませてはいけない。** ユーザーは crit の画面しか見ておらず、Claude Code のチャット欄は見ていないことが多い。

返信コマンドの詳細な作法 (フラグの意味、bulk import の JSON スキーマなど) は crit:crit-cli を参照する。
ここでは本ワークフロー特有の注意点だけを書く。

- **対象セッションは cwd (対象リポジトリ・ブランチ) から自動検出される。** `crit comment` に `--session` フラグは存在しないので、必ず対象リポジトリのディレクトリで実行すること
- body にシングルクォート・改行・コードブロックを含む場合は、件数によらず Write ツールで JSON ファイルを作ってから `--json --file` で投稿する。日本語の解説は 1 件でもこれらを含みやすい

**Approve や resolve はユーザーが明示的に求めない限り行わない。** このワークフローの目的は解説であって、レビュー完了の判定ではない。
