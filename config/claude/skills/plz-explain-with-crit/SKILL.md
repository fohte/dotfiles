# crit を Q&A の UI として使う

crit を「レビューツール」としてではなく、「対象の意味を質問できる UI」として使うためのワークフローである。
ユーザーは Approve するかどうかを判断したいのではなく、単に対象を理解したいだけである。
通常のレビュー運用 (approve に向けて指摘を潰していく) とは目的が違う。

## 全体の流れ

1. 対象を決め、対象別の reference を読む
2. 対象を用意して crit をバックグラウンド起動する
3. 起動ログに出た URL をそのままユーザーに案内する
4. (依頼があれば) 過去の履歴を消して一から開き直す
5. バックグラウンドタスクの完了通知を待つ
6. 通知の stdout に含まれるコメント (= ユーザーの質問) を読み、調査する
7. 回答を crit 側への返信として書き込む (チャットには書かない)
8. crit を再開して round を開き直す。**ここまでやって初めて返信がユーザーに届く**
9. 手順 5 に戻る。未解決の質問が無くなり approve された round まで、このループを続ける

対象によって変わるのは「起動コマンド」と「何を一次情報として読むか」だけで、それ以外の手順は共通である。

手順 7 と 8 は分割できない 1 セットである。
返信を書き込んだだけでは crit の画面には反映されず、ユーザーには何も届いていない。
**7 だけ終えた状態は、まだ「返信した」とは言えない。**

## 1. 対象を決めて reference を読む

| 対象                                                | reference                      |
| --------------------------------------------------- | ------------------------------ |
| GitHub PR、コミット範囲、リポジトリ内の既存ファイル | `references/code.md`           |
| これから解説用に生成する HTML                       | `references/generated-html.md` |
| 動作中の web app                                    | `references/live-app.md`       |

該当する reference を**起動前に**読む。
対象の準備手順、起動コマンド、そして手順 5 で当たるべき一次情報がそこに書いてある。
一次情報を取り違えたまま起動すると、質問が来てから調査先を探し直すことになる。

## 2. 起動する

**crit は Web UI サーバーを起動してブラウザ操作を待ち続ける、フォアグラウンドでは終了しないコマンドである。**
普通に Bash 実行すると呼び出し元がブロックされ続ける。
必ず `run_in_background: true` で実行すること。

crit のセッションは起動時の実行ディレクトリ、引数、git branch で識別される。
後続の `crit status` / `crit stop` / `crit comment` は起動時と同じディレクトリ、同じブランチで実行すること。
途中で checkout すると `crit status` が対象セッションを見つけられなくなる。

### URL は起動ログの文字列をそのまま案内する

**起動ログに出た URL の文字列をそのままコピーしてチャットに書くこと。**
「crit が起動しました」で終わらせて URL を書き忘れると、ユーザーは何も操作できない。

ホストとポートから自分で組み立てない。
対象の種類によってパスが付くことがあり (`/preview` など)、ルート (`/`) は crit の外枠 HTML を返すだけで対象は表示されない。

ポートも推測しない。
crit は同じ対象の既存 daemon を再利用するため、**新しく起動したプロセスが新しいポートを持つとは限らない**。
プロセス一覧の起動時刻やポート番号の若さから「これが自分のセッションだろう」と判断すると外す。
ポートを確認する必要があるときは `crit status --json` の `.sessions[] | select(.id == "<session-id>") | .port` を見る。

### 報告に書けるのは「起動した」と URL まで

`--no-open` を付けるとブラウザが自動起動しなくなるが、付けるにせよ付けないにせよ Claude 側からブラウザを開く手段はなく、**開いたかどうかを検証する手段もない**。
crit はビューアの接続状況を公開しておらず、`crit status --json` が返すのはセッションのメタ情報だけである。
HTTP で 200 が返ることも根拠にならない。
crit の外枠 HTML はどのセッションでもどのポートでも同一なので、200 が示すのは「crit のどれかが生きている」ことだけである。

「開いています」「表示されています」と書くと、開いていなかったときにユーザーは URL を探すところから始めることになる。

## 3. 履歴を消して一から開き直す

crit は同じ対象に対して過去に開いたセッションを自動的に再利用する。
Round 数が増え、現在の対象から外れた古いコメントが Outdated として残り続ける。
ユーザーが「一から」「クリーンな状態で」と言った場合はこれを消す。

```
crit status --json   # review_file のパスと session id を確認
crit stop            # 対象セッションの daemon だけを止める
```

`--all` を付けると他の無関係な crit セッションまで巻き込んで停止させてしまうので使わない。
ファイル指定で開いたセッションを狙うときは `crit stop <file>` と対象を明示する。
`crit status --json` の `review_file` (`~/.crit/reviews/<session-id>/review.json`) がまだ残っていれば、そのディレクトリを削除する。
これは git 管理下のファイルではなく crit のローカルキャッシュなので、消してよい。
その後もう一度同じ起動コマンドを実行すれば、真っさらな状態で開ける。

## 4. ユーザーの質問を拾う

バックグラウンドの crit プロセスは、ユーザーがブラウザ側で一定の操作 (Approve など) をすると終了し、タスク完了通知が届く。
**通知が来るまで sleep やポーリングで待たず、何もツールを呼ばずに待つこと。**

完了時の stdout に `approved: true/false` と、未解決コメントの一覧が JSON で入っている。
これがユーザーの質問そのものである。
ここで会話が完結したと思って放置してはならない。
中身を読んで次のステップに進む。

## 5. 調査して crit に返信する

質問ごとに、必ず一次情報に当たってから答える。
憶測で代弁しない。
何が一次情報かは対象で変わるので、手順 1 で読んだ reference に従う。

回答は crit 側への返信として書き込む。
**チャットに解説を書いて済ませてはいけない。** ユーザーは crit の画面しか見ておらず、Claude Code のチャット欄は見ていないことが多い。

返信コマンドの詳細な作法 (フラグの意味、bulk import の JSON スキーマなど) は crit:crit-cli を参照する。
ここでは本ワークフロー特有の注意点だけを書く。

- **対象セッションは実行ディレクトリから自動検出される。** 候補が複数あって曖昧なときだけ `crit status --json` で id を調べ、`--session <id>` を付ける
- body にシングルクォート、改行、コードブロックのいずれかを含む場合は、件数によらず Write ツールで JSON ファイルを作ってから `--json --file` で投稿する。日本語の解説は 1 件でもこれらを含みやすい

**Approve や resolve はユーザーが明示的に求めない限り行わない。** このワークフローの目的は解説であって、レビュー完了の判定ではない。

## 6. 返信を届ける

返信の書き込みは、レビューファイルを更新するだけの操作である。
round は閉じたままなので、**この時点でユーザーの画面には何も反映されていない**。

crit は round 完了時の stdout の末尾で、返信後に実行すべきコマンドを自分で指示してくる。
それを実行して round を開き直すまでが返信作業である。
手順 2 と同じくバックグラウンド実行し、再開後の URL を改めて案内する。

**これはユーザーに確認を取る場面ではない。**
「再開しますか」と聞いて止めると、ユーザーは届いていない返信を待ち続けることになる。
crit の出力に明示されている手順を、確認事項に読み替えない。

再開はトップレベルのセッション指定で行う。
`preview` のようなサブコマンドはセッション指定のフラグを受け付けないので、サブコマンド側に付けようとすると失敗する。

## 7. 状態は crit の出力から読む

状態を知りたいときは crit のコマンド出力を一次情報にする。
レビューファイルの生データやプロセス一覧を自前で読んで推測すると、次の 3 つで外す。

- レビューファイルの有無や更新時刻は状態の根拠にならない。
  初回 round が完了するまでファイル自体が作られず、一方で round 進行中の書き込みは随時反映される。
  「まだ無い」も「更新されている」も、書き込みの成否を判定できない
- 既存コメントへの返信として来た質問は、未解決コメントの一覧に本文が出てこない。
  一覧に出るのは親コメントの本文だけなので、返信まで含めて読む
- ユーザーの返信は投稿者名が空で入ることがある。
  自前でレビューファイルをパースするなら、コメントとその返信を素直に辿るだけにして、投稿者名の有無で絞り込まない

**「ユーザーの書き込みが見つからない」と報告する前に、まず自分の読み方を疑う。**
crit が保存していないのではなく、クエリが落としている方が多い。
