# 設計判断 HTML の内容確認

設計の採否を判断するために作った HTML の内容を確認する。一般の設計相談や、既存コード・PR・画面の閲覧説明と Q&A には適用しない。確認項目や作業記録をそのまま HTML に載せる必要はない。

## 入力と確認順

- 元の依頼と後続指示、その出典、判断に使った一次根拠、確認対象の HTML を揃える。
- まず依頼と根拠から重要なゴール・制約・利用場面を探す。設計側の課題一覧を網羅性の前提にしない。
- その後、ゴールから課題、策、変更後の仕組み、検証へ進み、逆向きにもたどる。

## 内容の確認

1. **要求とゴール**: 要求、事実、仮説、担当の提案を区別し、目的・成功条件・範囲・制約の根拠を追えるか。
2. **課題の分解と抜け**: 各課題がゴールを妨げる理由と現状との差が分かるか。必要条件と代替手段を区別し、利用場面・境界・失敗から課題一覧にない重要条件も探したか。
3. **策の導出と比較**: 各案がどの課題をどう変えるか根拠や仮説とともに説明できるか。比較する案は同じ目的・範囲・制約に対して成立し、併用策と代替案を区別しているか。成立する案が 1 案だけなら、その理由を示しているか。議論 (crit の返信やチャット) で却下した案がすべて、却下した範囲とユーザーが問題とした点を理由として HTML に残り、完成時点の判断材料として改稿履歴と区別されているか。
4. **変更後の仕組みと影響**: 採用案の作用が題材に必要な構成、処理、状態、責務、例外などに反映され、影響範囲が分かるか。
5. **検証と判断**: 検証がゴールや重要条件を確かめ、基準・計画と実施結果を区別しているか。未検証の効果を実証済みとせず、残る不明点と判断への影響を示したか。

## 要修正となる欠落

- ゴールから課題、課題から策、策から具体的な仕組み、仕組みから検証への接続を根拠とともに追えない。
- 元の依頼や重要な利用場面の条件が抜けている。
- 案の比較が異なる目的や範囲を混ぜている、または案の作用が説明されていない。
- 図や見出しは揃っていても、判断に必要な理由、影響、検証が欠けている。

指摘で設計の前提や採否が変わる場合は、影響する課題、案、仕組み、検証を更新して再確認する。表現や配置だけの修正では、影響する内容に絞って確認する。HTML には完成時点の判断材料を残し、改稿履歴は含めない。
