# 対象: 解説用に生成する HTML

コードや diff として存在しないもの (アーキテクチャ、調査結果、概念同士の関係、時系列) を解説する場合。
ユーザーは図の任意の箇所を選択して「ここは何」と聞けるので、チャットで長文を往復するより当たりを付けやすい。

設計の採否を判断する HTML を作る場合、またはその採否判断に影響する改稿をする場合に限り、`assets/design-outline.md` と `references/design-check.md` を読む。そこで扱うのは HTML 上の構成と内容の接続・抜けの確認であり、一般の設計相談に文書作成や独立照合を追加しない。既存コード、PR、動作中の画面の閲覧説明や Q&A だけの場合は読まない。

## 作るかどうか

図で説明できることがあるなら作る。
図が無くただの文章になるなら HTML にする意味は薄いので、普通にチャットで答える。

## 読み手は何も知らない

読み手は、この資料を書くために読んだコード、ログ、調査の経緯を一切見ていない。
書き手が作業中に頭に入れた文脈は、読み手の頭には無い。
わかりにくい資料は、ほぼすべてこの文脈を読み手も持っている前提で書いたことから生まれる。

その資料が何を決めるためのもので、結論は何か。
これを最初に言わなければ、読み手は何を見ればいいかわからない。
作業の判断を求める資料では、結論より前に作業の目的を書く。
目的とは、どんな問題を解くのか、終わると何ができるようになるかである。
how から始めると、読み手は目的が分からないまま判断することになる。
作業中に自分で付けた呼び名や略語は、読み手にとっては知らない言葉である。

## ストック資料として書く

HTML は crit でのレビュー後、社内共有の URL やタスクの page としてそのまま残る。
作業中の識別子や進行状況は、後から読む人には意味が通らず、すぐ古くなる。
次のものは書かない。

- タスク番号、session ID などの作業管理用の識別子
- 進行状況 (「approve 待ち」「レビューで判断する」「他タスクの merge 後に着手」など)
- 依頼元や他セッションとのやり取りの経緯

他の作業に触れるときは、番号ではなく中身で書く (「#12 の後に」ではなく「ログイン画面の改修の後に」)。
受け取った依頼文が番号や進行状況で書かれていても、そのまま写さない。

出典は残す。根拠にした issue、PR、ドキュメントは URL でリンクする。
リンク文字列は番号ではなく中身で書く (「#34」ではなく「キャッシュ方式を決めた PR」)。

ソースコードは commit SHA か release tag を含む GitHub の permalink で参照する (`https://github.com/<org>/<repo>/blob/<sha-or-tag>/<path>#L<n>`)。
branch 名の URL は、branch が進むと別の行を指すので使わない。
未 push の commit の SHA は 404 になるので、push してからリンクする。
`pkg/foo.go:37` のような path:line は、どの repo のどの時点のコードか分からず、ファイルが変わると別の行を指す。
リンク文字列には、何が書かれている箇所かを書く (「リトライ回数を決めている箇所」)。

## 絵で伝え、言葉は少なく

**図説をベースにし、文字は極力減らす。文字で書くのは、どうしても図にできない部分だけにする。**
図を見ただけで要点がわかる状態を目指す。
先に文章を書いてそれを箱と矢印に並べ替えても、図にはならない。
まず読み手に見せたい絵を決め、それから描く。

## 図解の設計

図を新規作成・更新する場合に限り、`diagram-design` skill の visual-type guide から題材に合う type reference だけを読む。コード、live app、既存図の閲覧時は読まない。挙動・状態・リスクが主題なら同 skill の `references/semantic-patterns.md` も先に読み、意味に合うパターンを選ぶ。図種、配置、線、ラベル、SVG accessibility と図自体の品質検査には `diagram-design` を使う。

図は既存 HTML の `<figure>` 内に inline SVG として置き、必要な CSS だけを `diagram-styles` に追加する。`shared-styles`、単一 HTML、ダーク固定、システムフォント、外部依存なしを維持する。既存の explainer theme を今回の図の明示指定として使い、`diagram-design` の onboarding、style guide の書換え、profile 保存に進まない。既定テンプレート全体や root/body CSS を移植せず、vendor ファイルも変更しない。

図の機械検査には `diagram-design` の `scripts/self_check.py` を使う。出典の外部 `a href` は `--offline` の有無にかかわらず失敗し、`--offline` では Google Fonts も拒否されるため、inline SVG と必要な `diagram-styles` だけを含む一時 HTML で実行する。資料全体に外部 CSS、JavaScript、font、image の読み込みがないことは別に確認する。

指摘への対応で情報を足すときも、まず既存の図に描き込めないか考える。文章や表を追記で足し続けると、最初は図が中心だった資料も文字が中心の資料になる。

書き上げたら crit を起動する前に読み返し、次のどれかに当てはまれば描き直す。
ユーザーに「文字が多い」と言われてから直すと、その往復が 1 round 無駄になる。

- 図の箱の中身が文になっている (文章を箱で囲んで矢印でつないだだけ)
- 図より文章や表のほうが画面を多く占めている
- 図を消しても内容が伝わる

図にできず残した日本語の文は、crit を起動する前に `/yomiyasu` (Codex: `$yomiyasu`) で書き直す。

図の形は、読み手が既に見方を知っているものを使う (テーブル構造なら ER 図、処理の順序ならシーケンス図)。
自作の形は、見方の説明から読ませることになる。

## 完成した HTML の文章を検査する

完成した HTML を crit に渡す前に、本文を抽出して yomiyasu の最新 lint に通す。

```bash
python3 <plz-explain-with-crit のスキルディレクトリ>/scripts/check_generated_html.py /path/to/output.html
```

この helper は `<p>`、見出し、`<figcaption>`、`<caption>` の文章をまとめて検査する。SVG は表示ラベルに使う `<text>` の内容だけを語彙検査し、本文と分けて処理する。CSS、JavaScript、HTML コメント、`<pre>` や `<code>` などのコード例、属性値は検査しない。inline 要素はタグだけを除いて文字列をつなぎ、文字参照を復元する。各指摘の `line` は元 HTML の行番号を示す。

抽出結果では太字や箇条書きの構造が失われるため、その比率は検査しない。出力の `prose_block_count`、`prose_char_count`、`svg_label_count`、`svg_label_char_count` で検査対象を見つけたことを確かめ、`candidate_count` が 0 件でも本文を読み返す。warn または error の候補があれば JSON を出したうえで終了コード 1 を返す。HTML を直した後は同じコマンドを再実行し、更新後の指摘を確認してから `crit preview` を起動する。

## 書く観点

どの資料にも、目的・結論・全体図・一次情報へのリンクを含める。
追加する観点は題材に合わせて選び、空の章や図と同じ説明文は残さない。

- 設計を判断する資料: 現状と変更後、選択肢と理由、制約と境界、変更範囲と検証方法
- 仕組みを説明する資料: 登場するもの、関係や順番、具体例、誤解しやすい箇所

## 表示する説明を選ぶ

理解や判断に必要な説明は HTML を開いた時点で読めるようにする。目的・結論・全体図・選択肢と理由などは折り畳まない。
出典一覧など、結論の理解や判断に必須でない補足は折り畳んでもよい。折り畳む場合は、含まれる情報が分かる見出しを付ける。

## テンプレートから作る

skill に同梱したテンプレートを使い、毎回新しい単一 HTML を作る。
`scripts/create-html.ts` は Bun の標準機能だけを使い、タイトルの設定と出力ファイルの作成を行う。
タイトルは HTML 用にエスケープされ、出力先が既にあれば失敗する。
本文用の JSON / YAML などの入力形式や、編集後のビルド工程は設けない。
設計判断を説明する HTML も、既存の `assets/explainer.html` と `scripts/create-html.ts` を使う。新しい生成オプション、script、本文入力形式は追加しない。

```bash
<skill-dir>/scripts/create-html.ts --title "架空の荷物が届くまで" --output /path/to/delivery-flow.html
```

生成した HTML の図と本文を直接編集する。
先頭の `shared-styles` は共通の配色・本文幅・余白・見出し・文字設定なので維持し、図に必要な CSS は `diagram-styles` に追加する。
図の HTML / SVG も同じファイルに書く。
テーマ変数を図にも使い、SVG の文字には `--font-sans` を指定する。
外部 CSS / JavaScript / font / CDN に依存させず、Mermaid を必須にしない。

テンプレートはタイトル、目的、結論、全体図、出典の配置を用意する。
本文は図を中心に直接書き、題材に合う章だけを追加する。

## UI を描くとき

実装済みの画面があるなら、実際の色・形・レイアウトを確認してから描く。
現物と食い違うモックは、提案そのものではなく食い違いについての質問を生む。

## 準備と起動

テンプレートから HTML を作り、図と本文を編集してから crit に渡す。
配色は常にダークモード固定で書く。
`prefers-color-scheme` によるライト/ダーク切り替えは不要。

設計判断を求める HTML では、crit を起動する前に `references/goldfish-review.md` を読み、Goldfish reviewer 3 体を実行する。指摘をすべて片付け、直し終えた HTML だけを crit に出す。

```
crit preview <file.html>
```

**`preview` は省略できない。** 拡張子から mode が推測されることはなく、`crit <file.html>` は files mode で開いて HTML を**ソースコードとして**表示する。
エラーにはならないので気付きにくい。
図を見て質問してもらうのが目的なので、レンダリングされる preview mode でなければ意味がない。

実行ディレクトリは任意だが、以降の `crit status` / `crit comment` を同じディレクトリで実行する必要があるので、どこで起動したか覚えておく。

図の要素には見出しやラベルを付けて、選択範囲だけでどこの話か特定できるようにする。
ラベルの無い矩形や矢印を選択されると、コメント本文だけでは何を指しているか分からない。

## 一次情報

**生成した HTML 自体は一次情報ではない。**
質問に答えるとき HTML を読み返してはならない。
それを書く根拠にしたソースコード、ドキュメント、ログ、調査結果に戻る。

自分が書いた要約を読み直しても裏は取れない。
元の要約が間違っていた場合、HTML を根拠に答えると同じ間違いを補強するだけになる。
「HTML にこう書いたから」は答えの根拠にならない。

## 図が間違っていたとき

質問に答える過程で図の誤りに気付いたら、返信するだけでなく HTML 本体も直す。
crit は元ファイルの変更を検知してブラウザを自動リロードするので、ユーザーの画面に即座に反映される。
誤った図を残したまま「返信で補足する」で済ませると、後から見返したときに図のほうが信じられてしまう。

## 議論で案を却下したとき

設計の採否を判断する HTML で案を却下したら、その判断を crit の返信やチャットで伝える前に、HTML の「選択肢と採否理由」へ書き足す。記録する案と理由は `assets/design-outline.md` に従う。
