# 対象: 解説用に生成する HTML

コードや diff として存在しないもの (アーキテクチャ、調査結果、概念同士の関係、時系列) を解説する場合。
ユーザーは図の任意の箇所を選択して「ここは何」と聞けるので、チャットで長文を往復するより当たりを付けやすい。

## 作るかどうか

図で説明できることがあるなら作る。
図が無くただの文章になるなら HTML にする意味は薄いので、普通にチャットで答える。

## 準備と起動

Write ツールで HTML を書いてから crit に渡す。

```
crit <file.html>
```

`.html` は preview mode として自動判別されるので `crit preview` と明示しなくてよい。
実行ディレクトリは任意だが、以降の `crit status` / `crit comment` を同じディレクトリで実行する必要があるので、どこで起動したか覚えておく。

図の要素には見出しやラベルを付けて、選択範囲だけでどこの話か特定できるようにする。
ラベルの無い矩形や矢印を選択されると、コメント本文だけでは何を指しているか分からない。

## 一次情報

**生成した HTML 自体は一次情報ではない。**
質問に答えるとき HTML を読み返してはならない。
それを書く根拠にしたソースコード・ドキュメント・ログ・調査結果に戻る。

自分が書いた要約を読み直しても裏は取れない。
元の要約が間違っていた場合、HTML を根拠に答えると同じ間違いを補強するだけになる。
「HTML にこう書いたから」は答えの根拠にならない。

## 図が間違っていたとき

質問に答える過程で図の誤りに気付いたら、返信するだけでなく HTML 本体も直す。
crit は元ファイルの変更を検知してブラウザを自動リロードするので、ユーザーの画面に即座に反映される。
誤った図を残したまま「返信で補足する」で済ませると、後から見返したときに図のほうが信じられてしまう。
