# 対象: 解説用に生成する HTML

コードや diff として存在しないもの (アーキテクチャ、調査結果、概念同士の関係、時系列) を解説する場合。
ユーザーは図の任意の箇所を選択して「ここは何」と聞けるので、チャットで長文を往復するより当たりを付けやすい。

## 作るかどうか

図で説明できることがあるなら作る。
図が無くただの文章になるなら HTML にする意味は薄いので、普通にチャットで答える。

## 書く前に決めること

Write ツールを開く前に次の 3 つを確定させる。
先に文章を書き始めると、調査ログをそのまま流し込んだものになる。

1. **何を判断するための資料か。** 案を選ぶのか、分解が妥当かを見るのか、現状を把握するのか。
   これに効かない情報は載せない。
   案を比較する資料に各案の詳細設計は要らない。
   検討の経緯、以前の版の誤り、実測の手順も判断には効かない。
2. **その判断に必要な構造は何か。** 関係ならコンポーネント図、階層ならツリー、複数案を同じ軸で評価するなら表。
   構造を文章で書くと、分解が MECE かどうかを読み手が判定できなくなる。
   図解を求められて文章を書き始めたら、その時点で要求を満たしていない。
3. **結論と推奨は何か。** 選択肢と判断材料を並べただけで終わらせない。

## 読み手に記憶と移動を要求しない

**「M1」「S2」「案 A」のような記号で対象を指さない。**
名前で呼ぶ。
記号は書き手の都合で、読み手は対応表を覚えながら読むことになる。
定義を近くに置けば済む話ではない。

同じ理由で「下記」「前述」「同上」も使わない。
補足を別セクションにまとめて参照させず、読む場所に実体を置く。

- 1 画面に収まらない縦長カードを並べない
- 観点が 3 つ以上に増えたらタブで分ける
- 図の要素はクリックで対応する説明へジャンプさせ、飛び先をハイライトする

## UI を描くとき

実装済みの画面があるなら、実際の色・形・レイアウトを確認してから描く。
現物と食い違うモックは、提案そのものではなく食い違いについての質問を生む。

## 準備と起動

Write ツールで HTML を書いてから crit に渡す。
配色は常にダークモード固定で書く。
`prefers-color-scheme` によるライト/ダーク切り替えは不要。

```
crit preview <file.html>
```

**`preview` は省略できない。** 拡張子から mode が推測されることはなく、`crit <file.html>` は files mode で開いて HTML を**ソースコードとして**表示する。
エラーにはならないので気付きにくい。
図を見て質問してもらうのが目的なので、レンダリングされる preview mode でなければ意味がない。

実行ディレクトリは任意だが、以降の `crit status` / `crit comment` を同じディレクトリで実行する必要があるので、どこで起動したか覚えておく。

図の要素には見出しやラベルを付けて、選択範囲だけでどこの話か特定できるようにする。
ラベルの無い矩形や矢印を選択されると、コメント本文だけでは何を指しているか分からない。

## 一次情報

**生成した HTML 自体は一次情報ではない。**
質問に答えるとき HTML を読み返してはならない。
それを書く根拠にしたソースコード、ドキュメント、ログ、調査結果に戻る。

自分が書いた要約を読み直しても裏は取れない。
元の要約が間違っていた場合、HTML を根拠に答えると同じ間違いを補強するだけになる。
「HTML にこう書いたから」は答えの根拠にならない。

## 図が間違っていたとき

質問に答える過程で図の誤りに気付いたら、返信するだけでなく HTML 本体も直す。
crit は元ファイルの変更を検知してブラウザを自動リロードするので、ユーザーの画面に即座に反映される。
誤った図を残したまま「返信で補足する」で済ませると、後から見返したときに図のほうが信じられてしまう。
