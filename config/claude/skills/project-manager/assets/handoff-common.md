## 進め方

1. **`/track-in-tq` を発動する。** 上記の tq タスクを `tq link <id>` でこのセッションに紐付ける。新しいタスクは作らない (既に存在する)
2. **調査する。** 原因が未特定なら root cause を特定するまで、現状の実装がどうなっているかを自分で調べる。ここは自己完結してよい
3. **設計は `/plz-explain-with-crit` でユーザーに出す。自分で確定させない。**
    - 設計案を crit に載せ、コメントで来た質問に一次情報を当たって答え、approve されるまで往復する
    - **返信を書き込んだだけではユーザーに届かない。crit を再開して round を開き直すまでが 1 セットである。**
    - 判断がユーザーに属するもの (何を運用に載せるか、どの外部サービスを契約するか など) も、勝手に決めず根拠付きで選択肢を示す
    - **crit の資料は、このタスクが何のためにあるか (どんな問題を解くのか、終わると何ができるようになるか) から書き始め、how はその後に置く。** how から始めると、ユーザーは目的が分からないまま判断することになる
    - **crit の資料はストック資料として書く。** tq のタスク番号、session ID、進行状況 (「approve 待ち」など)、PM とのやり取りは書かず、他のタスクには番号ではなく中身で触れる。資料は後で tq の page や共有 URL として残る。この引き継ぎ文や PM からのメッセージの言い回しを写すと、後から読む人には通じない
    - **出典とソースコードはリンクで示す。** 根拠にした issue、PR、ドキュメントは URL を貼る。ソースコードは path:line で書かず、push 済みの commit SHA か release tag を含む GitHub の permalink にする。どちらもリンク文字列は番号や path ではなく中身で書く
4. **approve された内容を tq の page に書く。** 設計・調査結果・根拠はここに置く。task description には書かない
5. **実装が必要なら `/delegate` で委任する。** 自分で実装しない。委任してよいのは設計が approve され、原因が特定できてからである。1 委任 = 1 PR。複数 PR に分かれる規模なら `/split-into-prs` で分割し、最初の 1 PR だけ委任して、残りは前の PR が merge されてから改めて委任する
    - **委任先の engine は既定のままにする。** `--engine` を指定しない
    - **`DELEGATE_TQ_TASK_ID` に上記タスクの ID を必ず渡す。** 渡さないと委任先の PR がどのタスクにも載らない
6. **節目ごとに引き継ぎ元 (PM セッション) に報告する。** 設計の approve 待ちになったとき、PR が出た / merge されたとき、止まったとき、終わったとき。`a agent peer parent | jq -r '.[0].session_id // empty'` で ID を取り、`a agent peer notify --message "<要約 + 成果物のパスや PR URL>" <session_id>` で送る。全文は貼らない

## 全体の文脈

<プログラム全体の目標と、全体像・完了条件が書かれた場所 (起点タスクの page など)>

**起点タスク (tq #<起点タスク番号>) の完了条件・仮定は書き換えない。** 狭める必要が出たら、狭めることをユーザーに明示して合意を取る。**tq の親子構造や依存関係も勝手に変えない。**

<現状: どこまで終わっていて、何が残っているか>

このセッションは PM セッションから切り出された作業セッションで、他の残タスクも並行して別セッションに配られている。自分の担当タスク以外に手を出さない。
