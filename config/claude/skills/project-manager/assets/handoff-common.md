## 進め方

1. **`/track-in-tq` を発動する。** 上記の tq タスクを `tq link <id>` でこのセッションに紐付ける。新しいタスクは作らない (既に存在する)
2. **調査する。** 原因が未特定なら root cause を特定するまで、現状の実装がどうなっているかを自分で調べる。ここは自己完結してよい
3. **設計は `/plz-explain-with-crit` でユーザーに出す。自分で確定させない。**
    - 資料の作り方と crit の往復は、すべてその skill に従う。approve されるまで往復する
    - 判断がユーザーに属するもの (何を運用に載せるか、どの外部サービスを契約するか など) も、勝手に決めず根拠付きで選択肢を示す
    - 設計に実装が含まれ、実装先リポジトリの `repo.direct_commit` が `true` でないなら、言われなくても `/split-into-prs` で PR 分割まで済ませ、分割案を設計資料に含めて出す。設計と一緒に分割も approve してもらえば、委任の前にもう一度承認を待たずに済む。ユーザーが分割を指定・承認済みなら分割し直さず、その案を載せる
4. **approve された内容を tq の page に書く。** 設計・調査結果・根拠はここに置く。task description には書かない。PR 分割も approve されたら、split-into-prs の「tq チェックリストへの記録」に従ってチェックリストにも記録する
5. **実装が必要なら `/delegate` で委任する。** 自分で実装しない。委任してよいのは設計が approve され、原因が特定できてからである。1 委任 = 1 PR。approve 済みの PR 分割に従い、最初の 1 PR だけ委任して、残りは前の PR が merge されてから改めて委任する
    - **委任先の engine は既定のままにする。** `--engine` を指定しない
    - **`DELEGATE_TQ_TASK_ID` に上記タスクの ID を必ず渡す。** 渡さないと委任先の PR がどのタスクにも載らない
    - PR 分割の実装チェックリストがある場合は、委任する PR に対応する葉項目 ID を `DELEGATE_TQ_CHECKLIST_ITEM_ID` に渡す。Batch 親の ID は使わない
6. **ユーザーが見ていない節目だけ引き継ぎ元 (PM セッション) に報告する。** 報告するのは、PR が merge されたとき、範囲が変わったとき、止まったとき、終わったとき。設計の approve 待ちになった、crit を開き直した、approve された、のようにユーザーが自分の画面で見ている出来事は報告しない。PM がそれをユーザーに中継し、同じ通知が二重に届いてトークンと費用の無駄になるため。`a agent peer parent | jq -r '.[0].session_id // empty'` で ID を取り、`a agent peer notify --message "<要約 + 成果物のパスや PR URL>" <session_id>` で送る。全文は貼らない

## 全体の文脈

<プログラム全体の目標と、全体像・完了条件が書かれた場所 (起点タスクの page など)>

**起点タスク (tq #<起点タスク番号>) の完了条件・仮定は書き換えない。** 狭める必要が出たら、狭めることをユーザーに明示して合意を取る。**tq の親子構造や依存関係も勝手に変えない。**

<現状: どこまで終わっていて、何が残っているか>

このセッションは PM セッションから切り出された作業セッションで、他の残タスクも並行して別セッションに配られている。自分の担当タスク以外に手を出さない。
