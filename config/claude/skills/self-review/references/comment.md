# Comment Review Reference

diff で追加・変更されたコード内コメント (行コメント・ブロックコメント・doc comment) の質を判定する。

最初に `references/_common.md` を読み、動作原則・禁止事項・出力形式ボイラープレートを適用する。本ファイルは comment 固有の差分のみを記述する。

このグループは diff で追加・変更されたコメントそのものを見る。drift 全般 (コード ↔ コメント ↔ doc comment ↔ README ↔ `--help` ↔ 仕様 / 規約) は convention 観点 10 の担当で、コメントとコードの矛盾は両者が重複して見る (重複指摘は skill 側の dedup で 1 件にまとまる)。

## 大原則: コメントの宛先は未来の読み手

コメントの読者は、レビュアーでも書いた本人でもなく、**この変更の経緯を一切持たずにそのコードだけを読む将来の誰か**。

「今この変更を説明したい」という動機で書かれたコメントは宛先を間違えている。経緯・判断の正当化・レビュアーへの補足は、コミットメッセージ・PR 本文・issue に置く。それらは変更を追う人が読む場所であり、コードを読む人が読む場所ではない。

コメントはコード本体と違ってテストも型チェックも効かないため、コードが変わっても修正されないまま残って腐る。腐ったコメントは無いより有害 (読み手が信じて誤る)。したがってコメントは資産ではなく負債であり、「あった方が親切」は書く理由にならない。

## 判定手順

追加・変更されたコメントを **1 件ずつ** 以下のテストにかける。1 つでも落ちたら指摘する。doc comment は「削除テスト」を原則免除するが例外があり、下記「書くべきコメント」の doc comment 項に従う。

1. **宛先テスト**: そのコメントが答えているのは「レビュアーの疑問」か「将来の読み手の疑問」か。前者なら PR 本文へ移す。
    - 落ちる例: 「〜も検討したが〜にした」「〜なのでここでは問題ない」「今回の変更で〜を追加」「既存の挙動は変えていない」
2. **削除テスト**: 消したら読み手がコードを誤読するか / 重要な制約を見落とすか。どちらも起きないなら消す。
    - 落ちる例: コードの言い換え (`// increment counter` の直後に `counter += 1`)、`// --- setup ---` のような区切り見出し、自明な getter/setter の doc comment
3. **コードで表現テスト**: そのコメントが補っている分かりにくさは、命名・関数抽出・型で消せないか。消せるならコメントを足すのではなくコードを直す (Suggestion にはリネーム・抽出後のコードを書く)。
    - 落ちる例: `// t は経過秒数` → 変数を `elapsed_seconds` にする。長い処理の途中に置かれた `// ここからバリデーション` → 関数に切り出す
4. **賞味期限テスト**: 時点依存の情報を含んでいないか。含むなら書かない。
    - 落ちる例: 過去 PR / issue 番号による経緯説明、「前回は〜」「今回は〜」「現在は〜だが将来的に」、移行途中であることの説明、採用しなかった選択肢への言及
    - 例外: 解除条件として参照する issue link (下記「workaround」) は時点依存ではなく **解除の判定材料** なので許容する
5. **正確性テスト**: コメントの主張が、同じ diff のコードと一致しているか。
    - 落ちる例: 引数の単位・デフォルト値・戻り値・throw する条件がコードと違う、条件分岐の説明が反転している、コピペで別関数の説明が残っている

## 書くべきコメント

以下は上記テストを通る。存在するのに書かれていない場合も指摘する (読み手が確実に間違える箇所のみ)。

- **外部制約**: そのコードが不自然な形をしている原因が外部にある場合 (API の仕様、ライブラリのバグ、プロトコル・ハードウェアの制約、他システムとの互換性)。コードを読んでも絶対に分からない情報
- **非自明な前提・invariant**: 呼び出し順序、保持が必要なロック、値の単位・範囲・精度、null / 空の許容、副作用の有無
- **workaround とその解除条件**: 何を回避しているか + いつ消せるか (upstream issue link や条件)。解除条件が書けない workaround は、そもそも workaround である説明が機能しない
- **意図的に間違いに見える箇所**: あえての非効率、あえての重複、あえて握りつぶす例外。無いと後続の読み手が「バグだ」と判断して直してしまう
- **doc comment (public API)**: 呼び出し側が実装を読まずに正しく使うための契約 (各引数の意味と単位、戻り値、投げる例外、副作用) を網羅的に書く。「読み手が驚く箇所だけ」の原則はここには適用しない。ただし引数名の言い換えだけの doc comment は削除テストで落とす

## 書くべきでないコメント

- コードから読み取れる事実の言い換え、区切り見出し
- 書き手の判断の正当化・弁明
- 変更履歴・経緯 (git が持つ)
- コメントアウトされたコード (git が持つ)
- 追跡先の無い `TODO` / `FIXME` / 「あとで直す」(issue link か具体的な解除条件が無いものは、消すか issue を作る)

## 重要度

- 🔴 **Critical**: コメントの主張がコードと矛盾しており、信じた読み手が誤る (単位・デフォルト・例外・条件の反転など)
- 🟡 **Warning**: 上記以外のテスト違反 (不要なコメント、宛先違い、時点依存、解除条件の無い workaround、必要な制約の未記載)

## 出力形式

```
## 観点別評価 (comment)

コメントの質: <マーカー> <一行>

## 指摘詳細 (comment)

(_common.md のテンプレに従う。指摘 ID は `CMT:<file>:<LINE>`。**観点** 行は `コメントの質` とする。ゼロ件なら "指摘なし" の 1 行)
```
