# Convention Review Reference

最初に `references/_common.md` を読み、動作原則・禁止事項・出力形式ボイラープレートを適用する。本ファイルは convention グループ固有の差分のみを記述する。

このグループはプロジェクト固有ルール遵守を担当する。**最初に必ず規約を読み込み、チェックリスト化する** こと。スキップは禁止。

## 規約読み込み (必須・最初に実施)

以下を最初に読み、禁止事項・必須事項・推奨パターンをチェックリスト化する。**スキップ禁止** — チェックはこのリストに基づくため、未読のままだとプロジェクト固有ルール違反を見逃す。

- `CLAUDE.md` (root + 該当サブディレクトリ)
- `.gemini/styleguide.md` (存在すれば): Gemini Code Assist が参照するレビュールール

## 担当観点

各観点について「この diff でこの軸は壊れうるか」を必ず一度問い、結論を出力に残す。番号は self-review 全体の通し番号 (prettier の再採番回避のため bullet 形式で記述)。

- **7. 可観測性 (Observability)**: ログ・メトリクス・エラー追跡・デバッグ可能性。
- **10. ドキュメント整合性**: コード ↔ コメント ↔ doc comment ↔ README ↔ `--help` ↔ 仕様 / 規約 の drift。コメントがコードと矛盾しているケースは、そのコメントを diff で触っているかどうかを問わず扱う (comment reviewer の trigger は行単位の正規表現なので、複数行コメントの本文だけを書き換えた変更では起動しない)。コメントの要否・宛先・書き方の質判定は comment reviewer の担当なので扱わない。
- **11. プロジェクト規約遵守**: 上記「規約読み込み」で読んだルールに違反していないか。違反指摘時は **必ず規約ファイルの該当行を引用** する。引用できるルールが無い複雑性・重複・抽象化の問題は structure reviewer の観点 8 の担当なので扱わない。

## 固有原則・重要度補足

- 規約違反指摘では **必ず** 規約ファイルのパス、行番号、該当文言の引用を併記する。
- 🔴 Critical の典型例: ドキュメントが嘘になっている (古い API を `--help` が説明している等の drift) / 致命的な観測欠如 (失敗が silent)
- 🟡 Warning の典型例: 規約違反 / minor な doc drift

## 出力形式

ヘッダは `## 観点別評価 (convention)`。出力では番号付きリストではなく bullet `-` を使い、各行頭に `<番号>.` を手動で書く (prettier の自動再採番を回避するため):

```
## 観点別評価 (convention)

- 7. 可観測性: <マーカー> <一行>
- 10. ドキュメント整合性: <マーカー> <一行>
- 11. プロジェクト規約遵守: <マーカー> <一行>

## 指摘詳細 (convention)

(_common.md のテンプレに従う。規約違反は **Rule violation** ブロック必須。ゼロ件なら "指摘なし" の 1 行)
```
