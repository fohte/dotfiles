# tq でタスクとして作業を追う

作業を tq のタスクとして立て、進行に合わせて状態を更新し、終わったら閉じるまでを担当する。

一度発動したらセッションの間は有効なままにする。
各ステップの指示を待たず、下記の節目に到達した時点で自分で実行する。

`tq` CLI のフラグ、`--author` の指定、長文を `--file` で渡す作法は `tq` skill を参照する。

## 節目

| 節目                             | やること                                                                                                    |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 作業に着手する                   | 既存タスクを探し、使う / 作る / 作らないを判定する。使うか作るなら `in_progress` にしてセッションを紐付ける |
| 設計・調査がまとまった           | page を作る                                                                                                 |
| 設計が変わった                   | 既存 page を更新する                                                                                        |
| PR が merged になった            | 残作業の有無を確認する                                                                                      |
| 残作業が無くなった               | まとめコメントを書いて `complete` する                                                                      |
| 残作業があるのに完了扱いになった | `todo` に戻す                                                                                               |

## 着手する: 作るか、使うか、作らないか

まず既存を探す。
ユーザーが手で作っていることが多く、同じ作業にタスクが 2 つあるのは 0 個より悪い。
履歴が両方に散って、どちらも記録として使えなくなる。

```bash
tq task search '<キーワード>'
```

`--status` は値を 1 つしか取れないので付けない。
`completed` の一致も判断材料になる。
同じ作業が一度完了しているなら、今回のはその続きであって新規ではない。

- 該当するタスクがある → それを使う。2 つ目を作らない
- 無く、PR や成果物が出る作業 → 作る。これは下限であって上限ではない。後から振り返る価値のある調査も作る
- 無く、痕跡が残らない作業 (質問への回答、設定 1 行の変更) → 作らない

作るのは着手時であって完了時ではない。
終わってから作ったタスクは領収書で、作業中の進捗をユーザーが見られない。

作るときは、このセッションが他セッションからの委任先かどうかを確認する。
`TQ_PARENT_SESSION_ID` が環境にあれば委任先で、その値と `sessionId` が一致するセッションを `tq session list` から探すと、委任元が紐付けたタスクが `tasks[]` に入っている。
`tasks[]` が 1 件なら、それを `tq task create --parent-id <親タスクの id>` に渡して委任元のタスクの子として作る。
`tq link` は呼ぶたびに紐付けを積み重ねるだけで前のリンクを外さないため、`tasks[]` は複数件になり得る。
委任元が無い、紐付くタスクが見つからない、または複数件で一意に決まらないときは親無しで作ればよく、そこで作業を止めない。
既存タスクを使う場合はこの判定をしない。
委任先が既存タスクの親を勝手に付け替えると、ユーザーが意図した構造を壊す。

作った場合も既存を使う場合も `tq task status <id> in_progress` にし、`tq link <id>` で今動いているセッションをそのタスクに紐付ける。
作業しているのに `todo` のままだと、ユーザーからは何も始まっていないように見える。
`tq link` はセッションを `TQ_SESSION_ID` から特定するので、渡すのはタスク ID だけでよい。
作らないと判定したときは、この節目自体が発生しないのでリンクもしない。

## 何をどこに書くか

| 置き場所         | 書くもの                                           |
| ---------------- | -------------------------------------------------- |
| task description | 1-2 行。何をやる作業で、なぜやるか                 |
| page             | 設計、調査結果、HTML 可視化。長いものは全部ここ    |
| comment          | 完了報告。何が入ったか、どの PR か、何を判断したか |

description に詳細を書かない。
書きたくなったらそれは page の内容。

実装中に設計が変わったら、新しい page を作らず既存 page を更新する。
古い方針を書いたまま残った page は、page が無いより誤解を招く。
既存 page に乗る前には読む。
現状より古いことがある。

## 閉じる

`complete` してよいのは次の両方を満たすときだけ。

- 立てた PR が全部 merged になっている。PR を伴わない調査だけの作業なら、この条件は無い
- 落とした項目 (「今回やらないこと」) が別タスクになっているか、ユーザーに提示済み

片方でも欠けるなら `complete` せず `tq task status <id> todo` に戻す。
残作業をまとめコメントに書いた上で完了にすると、閉じたタスクの中に未着手の作業が埋まる。

PR 番号は下記のように tq task へのリンク化を避けた形で書く。
詳細は `tq` skill の「Cross-reference other systems by URL, not by `#number`」を参照する。

まとめコメントの型:

```md
<冒頭 1 段落: 何ができるようになったか>

## PR 一覧

| PR                                                     | 内容 |
| ------------------------------------------------------ | ---- |
| [my-app #140](https://github.com/acme/my-app/pull/140) | ...  |

## やったこと

<判断とその理由。読み手が変更の形をつかむのに要ること>

<動作確認をしたなら、その結果>

<設計 page と結果がずれたなら、その差分>
```

PR が無い作業では `## PR 一覧` ごと省く。

詳細は page に置き、コメントからは参照する。
両方に書くと片方だけ古くなる。
